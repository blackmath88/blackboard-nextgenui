## Decisions and privacy behavior

`.pilot/context.json` is an atomic, hand-editable project setting with `rev`,
`share.board`, `changedBy`, `changedAt`. Missing means off. Invalid/unreadable
means off with `fileErrors`, including after a previously valid on setting;
there is no last-good sharing fallback. Broken files are not overwritten.
`/context share board on|off` serializes changes, increments rev, records user/time,
a system transcript line and `context_share`. `/state` includes the setting/rev,
recipient summary and previews. The page updates it through the existing SSE
watcher and selective state refresh. `/context` prints the exact additional chat
system object and per-role recipient/locality, policy, payload templates and
skip reason; future user/reply text uses explicit placeholders.

Default conversation-only applies to **all roles**, following the coordinator's
review-driven scope clarification. Chat uses only conversation history.
Extraction uses only the current user/assistant turn plus instructions/schema;
server-side quote/schema validation and near-duplicate checks remain. Sharing on
adds existing item titles to extraction as before. Omitting them can increase
redundant model suggestions and reduce model-side dedupe quality; duplicates are
still dropped server-side. Frame calls require both board sharing and the existing
frame experiment/consented usable panes. Otherwise sharing-off frame work is
skipped with `frame_skip` reason. Legacy duplicate/frame fixtures that require
model-visible board items explicitly opt in, rather than weakening the new default.

Every chat attempt logs `context: {board: boolean, items: count}` on `model_call`
(success/failure, including fallback); the count reflects actually included
items, without text. A separate `chat_context` records requests even when no
candidate is configured. Shared stats formatting exposes those events identically
through `/stats` and the read-only stats script. Pins, local-to-cloud fallback
prohibition unless `allowCloudFallback`, no fallback after partial output,
proposal validation and consent/rev checks are unchanged.

## Key storage and authority-rule exception

Keys resolve environment first, then the user-level
`${XDG_CONFIG_HOME:-~/.config}/pilot/secrets.json`, never via project data.
The task explicitly authorizes this narrow exception to v1 Authority rule 5
("The pilot never touches files outside .pilot/ and its own folder"). Keeping
credentials out of projects avoids exporting them with a blackboard or checking
them into a project checkout. This exception does not authorize arbitrary paths
or model-driven filesystem access. `PILOT_SECRETS_FILE` is a test-only explicit
absolute fixture path, used by every M1/browser test; empty/relative overrides
are refused rather than falling back to a real user store.

The private directory is created 0700, file/temp 0600, unique temp uses exclusive
creation, file fsync precedes same-directory atomic rename. Reads use no-follow
open plus fstat regular-file/UID/mode checks; symlinks, group/other or executable/
special permissions, wrong owner and invalid JSON are refused with value-free
errors. Existing insecure paths are not silently repaired/adopted. Single-process
read/modify/write is synchronous. Multiple Pilot processes can race and lose
unrelated saves; no cross-process locking is claimed. Parent replacement by a
hostile same-user process is outside the protection; atomic rename is not a full
crash-durability guarantee for the directory entry.

Settings permits only configured keyEnv names, trims saves, rejects blank,
control/newline and >4096-character values. Status returns names and only
`env|saved|missing`, never values, partial values or lengths. Environment overrides
saved values; Remove only deletes the saved value. The keyboard-reachable dialog
uses password fields, clears them after attempted Save/Remove and on Close,
and does not store values in browser storage. `/key` opens it, `/key status`
reports source. Common key-shaped chat/command lines are rejected before user
transcript/model dispatch; hints never repeat the token. This is a heuristic,
not detection of arbitrary credentials embedded in ordinary prose.

## Threat model and boundaries

Saved keys grant paid-provider authority. The server binds loopback and every
request checks Host exactly `127.0.0.1:<port>` or `localhost:<port>` against DNS
rebinding. Every non-GET requires an exact allowed HTTP Origin, or **absent**
Origin plus `x-pilot: 1`. A hostile present Origin cannot be overridden by the
header. The page always sends the header and existing curl/why clients were
updated minimally. All rejected requests return 403 before body processing and
record a fixed reason only. No CORS permission is enabled. This prevents drive-by
websites from spending keys; it is not authentication against local processes.

Key values exist transiently in the Settings POST, server memory and provider
Authorization header. Stored values are never returned to the page; never copied
to process.env, transcript, metrics, SSE or project files. Provider HTTP error
bodies are discarded before logging/propagation. Successful output is filtered
for the active credential, retaining matching prefixes across delta boundaries
so a split reflection cannot reach the stream/transcript. Endpoint control and
provider retention remain trust boundaries; unrelated keys/text cannot be inferred
by this filter. Same-user malware, extensions, browser developer tools, memory/
core dumps, user-config backups and already-sent provider data are not protected
by file modes. Turning sharing off cannot retract prior conversation contents or
in-flight/completed model requests. Existing config is trusted to choose endpoints.
